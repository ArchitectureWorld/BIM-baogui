# MVD IFC 规范化导出设计

## 背景

Revit 2020 中的 Stage01 已能按官方 H-IFC 参数映射写入坐标数据。实机导出的 IFC4 文件证明：

- `IfcProject` 已关联 `申报信息属性集`；
- `基点坐标X`、`基点坐标Y`、`基点高程` 已导出为 `IfcReal`；
- X、Y 和高程保持米制输入值，没有再次按英尺换算；
- 官方导出器仍会去除 MVD 属性名中的空格，将部分 `IfcLabel`、日期类型退化为文本，并把内部兼容参数重复导出到通用“数据”属性集。

这些差异发生在官方导出器生成 IFC 的阶段，继续修改 Revit 参数写入不能解决严格 MVD 命名和类型问题。

## 目标

新增 Stage04 MVD IFC 规范化组件。组件读取官方 H-IFC 已导出的 IFC 文件，保留几何、空间结构和非目标数据，仅按项目内 MVD 映射修正目标属性，然后写出新的 IFC 文件。

完成标准：

1. 源 IFC 始终保持不变。
2. 输出文件与源 IFC 位于同一目录，默认文件名为 `<源文件名>-MVD.ifc`。
3. 不创建 `.bak`、`.backup` 或时间戳备份文件。
4. `IfcProject` 上的 MVD 属性集、属性名、数据类型和值通过结构化验收。
5. 失败时不留下半成品输出，JSON 失败报告写到活动 GHA 所在目录。

## 非目标

- 不重写官方导出器的几何导出能力。
- 不修改或替换官方 H-IFC 插件文件和配置。
- 不覆盖源 IFC。
- 不删除与 MVD 无关的 Revit、官方插件或第三方属性集。
- 本阶段不自动操作官方 H-IFC 导出窗口。

## 用户工作流

1. 用户运行 Stage01，把报规数据写入 Revit。
2. 用户使用官方 H-IFC 导出 IFC。
3. 用户把官方 IFC 路径连接到 Stage04，并将 `Run` 从 `false` 切换为 `true`。
4. Stage04 完成解析、规范化、原子写出和验收。
5. 组件输出成功状态、目标 IFC 路径和逐项验收消息。

## 组件接口

### 输入

- `执行 / Run`：仅在 `false -> true` 边沿执行一次。
- `源IFC / Source`：官方 H-IFC 导出的 `.ifc` 文件绝对路径。
- `输出IFC / Destination`：可选。为空时在源文件旁生成 `<源文件名>-MVD.ifc`；不得等于源路径。

### 输出

- `成功 / Success`：解析、写出和回读验收全部通过时为 `true`。
- `状态 / Status`：等待、执行中、成功或失败。
- `输出IFC / Output`：成功输出文件的绝对路径。
- `消息 / Messages`：规范化数量、验收结果和故障说明。

## 架构

### `MvdIfcNormalizationCatalog`

从现有注册表生成规范化规则，以 `IFC 实体 + 属性集名称 + 属性名称` 作为键。规则包含：

- 规范属性名；
- 允许的官方别名，例如 `基点坐标X` 对应 `基点坐标 X`；
- 目标 IFC 数据类型；
- 单位和必填策略；
- 内部兼容参数名称，用于识别 `HIFC.<属性集>.<属性>` 重复项。

规则只维护一份来源，不在规范化器中硬编码第二套 166 项清单。

### `IfcStepModel`

实现面向本任务的 IFC STEP 结构解析层，负责：

- 保留原文件头、实体编号、参数顺序和未知实体文本；
- 正确识别 STEP 字符串、转义、嵌套括号和引用列表；
- 索引 `IfcProject`、`IfcRelDefinesByProperties`、`IfcPropertySet` 和 `IfcPropertySingleValue`；
- 仅重写需要变化的属性实体；
- 支持 IFC4 本次验收所需的简单值类型。

解析失败必须终止，不允许退化成全文件正则替换。

### `MvdIfcNormalizer`

执行以下顺序：

1. 验证源路径、扩展名、目标路径和文件可读性。
2. 解析 IFC schema；首版只接受 `IFC4`，其他 schema 明确失败。
3. 从 `IfcProject` 的属性关系开始定位目标属性集。
4. 将官方别名改为 MVD 规范名称。
5. 按 MVD 数据类型重建 `IfcPropertySingleValue.NominalValue`，例如 `IfcText -> IfcLabel`、日期文本转换为 IFC4 日期类型。
6. 保留已经正确的 `IfcReal` 数值，不做单位换算。
7. 从通用“数据”属性集中删除可确认由本插件创建的 `HIFC.` 重复属性引用；如果属性集因此为空，再删除对应关系和属性集。
8. 写入同目录临时文件，重新解析并验收后以原子移动生成目标 IFC。
9. 无论成功或失败都清理临时文件。

不会删除 `IfcBuilding` 上的同名正式属性集，因为额外存在不等于违反 `IfcProject` 必须存在的要求，且删除可能影响官方插件语义。

### `MvdIfcValidator`

对输出执行独立回读验收：

- schema 为 IFC4；
- 至少存在一个 `IfcProject`；
- `IfcProject` 关联目标属性集；
- 当前文件中存在值的 MVD 属性使用规范名称和目标类型；
- 坐标和高程为有限 `IfcReal`，且与规范化前正式属性值一致；
- `IfcProject` 的通用“数据”属性集中不再包含本插件创建的 `HIFC.` 重复项；
- 输出文件不是空文件，且实体引用可解析。

## 文件和失败处理

- 目标 IFC 不得与源 IFC 相同。
- 如果默认目标已存在，组件失败并要求用户指定新目标；不自动覆盖、不自动改名、不生成备份。
- 临时文件名使用目标目录内的唯一 `.tmp` 文件，并在结束时清理。
- 失败报告沿用 Stage01 JSON 报告风格，命名为 `BIMBaoGui.Stage04.failure-<时间戳>.json`，写入活动 GHA 目录。
- 报告包含源路径、目标路径、阶段、异常类型、消息和规范化计数，不包含 IFC 全文。

## 测试策略

### 单元测试

- STEP 参数切分支持嵌套括号、引用列表、Unicode STEP 字符串和转义引号。
- 官方别名映射为带空格的 MVD 属性名。
- `IfcText` 按规则转换为 `IfcLabel`。
- 正确的 `IfcReal` 数值保持不变。
- 仅删除已识别的 `HIFC.` 重复属性，不删除通用“数据”属性集中的其他属性。
- 源路径等于目标路径、目标已存在、非 IFC4、引用损坏时明确失败。

### 集成测试

使用最小 IFC4 fixture 构造 `IfcProject -> IfcPropertySet -> IfcPropertySingleValue` 关系，验证规范化后的文件可重新解析，实体引用有效。

### 实机验收

对文件 `20260802170320_20260731test02-v090-validation_模型打开后未操作过扩展属性_20260802170625.ifc` 生成新的 `-MVD.ifc`，确认：

- `基点坐标 X = 3373266.866`，类型为 `IfcReal`；
- `基点坐标 Y = 38589642.165`，类型为 `IfcReal`；
- `基点高程 = 24.0`，类型为 `IfcReal`；
- 项目编号和项目名称使用 `IfcLabel`；
- 源 IFC 的 SHA-256 在处理前后不变；
- GHA 目录中仍没有备份 GHA/DLL 文件。

## 发布

- 版本仍保持 `0.9.0.0`，本轮作为同一修复分支的硬化增量。
- Release 构建成功后只覆盖活动 `BIMBaoGui.Stage01.gha`。
- 部署前要求 Revit、Rhino.Inside 和 Grasshopper 已关闭，避免锁文件和混载旧程序集。
- 不在 GHA 目录创建插件备份；回滚依赖 Git 提交和可重复构建。
