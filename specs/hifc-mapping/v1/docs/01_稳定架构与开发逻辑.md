# GH / Rhino.Inside.Revit H-IFC 开发基线 v1

## 1. 稳定结论

本项目不依赖 HIFCTool 运行。HIFCTool 只作为规则和行为证据来源。

系统唯一真源不是 Revit 参数，也不是 GH 数据树，而是 **Canonical HIFC Data Graph（统一 HIFC 数据图）**：

```text
项目上下文 + Revit 模型扫描
        ↓
规则解析器 Rule Resolver
        ↓
Canonical Object Graph + Property Values   ← 唯一真源
        ├─ Revit Projection：共享参数/可视化镜像
        └─ IFC Projection：基础 IFC + 精确后处理
```

这解决四个根本问题：

1. 相同中文属性名在不同 Pset 中重复；
2. Revit 无原生 IfcOrganization、IfcSpatialZone 等稳定宿主；
3. Revit IFC Exporter 不同版本对实例/类型和自定义 Pset 的行为差异；
4. GH、Revit 参数和最终 IFC 三套数据容易失去同步。

## 3. 固定数据流

```text
01 InitializeFile
   → 生成 ProjectContext
02 ResolveRules
   → 从 166 条官方规则筛出当前模型适用集合
03 ScanModel
   → 生成 CanonicalObjectGraph
04 ResolveValues
   → 自动计算、模型读取、项目导入、人工填写
05 Persist
   → 先写 Canonical DataStore，再镜像到 Revit 参数
06 ValidateRevit
   → 对象、类型、单位、值、关系检查
07 ExportBaseIfc
   → Revit 原生 IFC 负责几何和基础实体
08 EnrichIfc
   → 按 canonical ID 精确创建/挂接 Pset、Organization、SpatialZone
09 ValidateIfc
   → 逐条核对 166 条属性及对象关系
```

## 4. 参数命名与 GUID

不使用纯中文属性名作为 Revit 参数唯一键。实际参数名固定为：

```text
HIFC.<PropertySet>.<IFCProperty>
```

例如：

```text
HIFC.建筑技术信息属性集.建筑高度
```

参数 GUID 由固定 UUIDv5 命名空间 `57736bb8-c060-558c-85d9-18226a3e3a4f` 和以下 canonical key 确定生成：

```text
标准 | 场景 | IFC实体 | PropertySet | IFC属性
```

因此同一条规则在任何电脑、任何文件和任何版本中都生成同一 GUID；同名“备注”位于不同 Pset 时不会冲突。

## 5. 官方数据与实施决策必须分开

每条记录分为三段：

- `official`：从 HIFCTool 提取，不允许开发者随意修改；
- `canonical`：我们的稳定 ID、GUID、参数名、数据类型；
- `implementation`：承载对象、值来源、适用性和导出策略。

当前官方文件只证明 166 条属性、16 个 Pset、9 类 IFC 实体及数据类型；**没有证明必填/有条件/建议**。因此 `requirementLevel` 统一保持 `UNCLASSIFIED`，之后必须从报规指南和检查软件规则中合并，不能把示例值误当成默认值。

## 6. IFC 导出策略

第一版不复制官方 DuckDB/Parquet 全链路，采用可验证的等价实现：

```text
Revit 原生 IFC：几何、层级、原生构件实体
        +
IFC 后处理：官方 Pset、属性、Organization、SpatialZone、精确关系
```

这样既保留 Revit IFC Exporter 的成熟几何能力，又避免被其自定义属性集兼容性锁死。

## 7. Revit 承载决策

| IFC 实体 | Canonical 对象 | Revit 可视承载 | 最终导出 |
|---|---|---|---|
| IfcProject | PROJECT | ProjectInformation | 后处理挂接 |
| IfcBuilding | BUILDING | ProjectInformation | 原生对象 + 后处理属性 |
| IfcBuildingStorey | STOREY | Level | 原生对象 + 后处理属性 |
| IfcSpace | SPACE | Room | 原生对象 + 后处理属性 |
| IfcDoor | DOOR | Door instance | 原生对象 + 后处理属性 |
| IfcDuctSegment | DUCT_SEGMENT | Duct instance | 原生对象 + 后处理属性 |
| IfcSite | SITE | ProjectLocation + DataStore | 后处理挂接 |
| IfcOrganization | ORGANIZATION | DataStore | 后处理创建/挂接 |
| IfcSpatialZone | SPATIAL_ZONE | Area 或 DataStore | 后处理创建/挂接 |

## 8. 事务规则

每次 GH 写入必须执行：

```text
Validate Command
→ TransactionGroup
→ Canonical DataStore revision +1
→ Parameter.Set / object update
→ Commit
→ Document.Regenerate
→ Read-back verification
→ 成功则 Assimilate；失败则 RollBack
```

写入接口必须携带 `expectedRevision`，防止界面旧值覆盖新值。

## 9. 错误模型

所有模块统一返回：

```json
{
  "success": false,
  "diagnostics": [
    {
      "code": "PARAMETER.TYPE_MISMATCH",
      "severity": "ERROR",
      "objectId": "building:main",
      "propertyId": "...",
      "message": "建筑高度要求 Length/Double，当前为 Text/String",
      "revitElementUniqueId": "...",
      "fixAction": "RECREATE_PARAMETER"
    }
  ]
}
```

禁止只返回 `false` 或“导出失败”。

## 10. v1 完成定义

v1 不是“界面能填”。必须同时满足：

1. 166 条官方规则完整载入且 schema 校验通过；
2. canonical ID 与 GUID 在重复运行中完全一致；
3. Project/Building/Storey/Space/Door/Duct/Site/Organization/SpatialZone 九类对象都有固定承载策略；
4. 自动计算值与手工值都进入统一数据图；
5. Revit 预检能够给出逐条断点；
6. 导出的 IFC 中 166 条规则逐条可核对；
7. 至少建立 1 个通过官方检查软件的 Golden IFC 回归样本。
