# 0.3.2 · 成功案例构件识别

用户确认先以“测试文件/01/成功通过HIFC”中的三个报规案例为参考。本次修正把成功 IFC 的构件对应证据接入当前 RVT 全面检查，并区分“已确认”“待确认分类”和“参考项未找到”。它不扩充官方必填规则，也不把参考案例数值复制到当前模型。

## 此前为什么漏识别

0.3.1 已能把模型类型识别为“总图”，但具体业务构件的识别仍主要依赖业务名称。RVT 的“场地”“绿化”“回车场”“规划红线”与成功 IFC 的业务分类不同；笼统的“道路”也不足以区分道路红线与道路边界线。此前只接入了案例属性集清单，没有接入 IFC 与 RVT 的逐构件对应关系。

另外，“总平构件”类型集完成状态会遮住实例的待分类状态。0.3.1 的实机测试覆盖扫描、写入和窗口生命周期，没有断言这些已知案例业务构件必须被识别，因此流程测试通过仍遗漏了业务识别问题。

表中的数字用于人工定位。程序匹配要求模型范围和 Revit UniqueId 对应，并重新核对当前名称、类型、类别及实体载体；不会只凭相同数字 ID 识别其他工程。模型已改名、改类型或改载体时，该证据只进入待核对清单。

补充证据保存于 `reference/success-case-01/recognition-evidence.json`，包含 IFC 文件及哈希、STEP、GlobalId、Revit Tag、原 RVT 哈希、快照哈希和当前载体信息。生成工具为 `tools/build_recognition_evidence.py`。原有冻结案例清单保持不变。

## 检查与写入

1. 人工确认阶段，再自动识别或人工指定模型类型。
2. 每次重新读取全项目；候选构件在清单中显示业务类别及“识别依据”。
3. 已核对身份的案例对应关系、载体支持的明确业务名，可进入整批分类和缺参数补齐预览。只有别名的对象保留为候选，需人工选择业务分类。
4. 预览确认后写入，回读校验，自动全量复检。既有明确分类予以保留；多候选和载体矛盾不自动写入。
5. 左侧分类清单分别显示已确认数和候选数。已有候选的类别显示“待确认分类”，不再直接算作模型缺失；通用类型属性完成不再遮住实例候选。

材质及辅助资源继续排除。链接模型继续提示在源文档检查。字段存在、有效值和业务模型补全分别显示，不把程序通过率当作模型合规率。

## 停车位保留人工核对

RVT 中 455344、455815 名为“停车位”，实际载体是通用模型。成功 IFC 的停车位属性集挂在两个 IfcSpace 上，STEP 为 210、350，且没有可对应的 Revit Tag，现有证据不能证明它们与这两个 RVT 通用模型是一一对应的。

其中 455815 还在案例中出现“名称为停车位、挂道路边界线属性集”的矛盾。程序展示这两类证据，禁止其进入自动批量分类；不擅自修改几何、转为 IfcSpace 或照搬错误分类。

## 插件加载隔离

本轮实机启动发现本机另一个 `H-IFC/Hifc.Revit.dll`。在 .NET Framework 中先加载它，再按 V1 路径加载同名程序集，实际返回的是前者；证据为 `validation/assembly-isolation-red.json`。V1 改用独立程序集名 `Hifc.V1.Revit.dll`，安装目录与功能区仍为 Hifc.V1 / H-IFC V1。改名后的独立加载验证见 `validation/assembly-isolation-green.json`。

安装会先备份旧 V1，再清理自己目录内过期的同名 DLL/PDB；不修改另一套 H-IFC 或 BIMBaoGui 插件。
